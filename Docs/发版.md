# CATVBA R2018 发布门禁与回滚手册

> [!CAUTION]
> **Status:** CURRENT — NO-GO policy；DRAFT — future release process
>
> **Validated:** 2026-07-13
>
> **release_eligible:** `false`
> **Scope:** 第 1 节的当前 NO-GO 与禁止事项立即有效；第 2-9 节是待整体设计书面批准的未来流程草案，不授权实施

当前仓库没有可发布的 R2018 CATVBA。根目录两个 CATVBA 是遗留取证样本；现有
`.github/workflows/auto-release.yml` 也不是合格发布器。任何文件存在、旧版本号、tag、工作流成功、
源码静态检查或本地 ZIP 都不能替代 B28 构建和 G0-G7 证据。

当前状态与下一动作以 [STATUS.md](STATUS.md) 为准，设计和证据边界以
[文档索引](README.md) 规定的权威链为准。

## 1. 当前禁止事项

在 G7 为未过期 `PASS` 前，禁止：

- 把根目录或 Git 历史中的旧 CATVBA 复制到 Release、共享盘或 Production；
- 从旧 CATVBA `Save As` 创建新候选，或把它作为回滚 seed；
- 通过合并无共同祖先的 `main`/`dev`、整树选边、squash 全分支来制造发布树；
- 批量删除/重建标签、裸推送分支或标签、绕过受保护分支/环境；
- 由文件名 glob 自动选择 CATVBA，或由一次 tag push 直接创建正式 Release；
- 把 Linux CI、本地 Python 测试或 Office VBA 当作 CATIA B28 Compile；
- 在现场热改 Production CATVBA 后继续沿用原哈希、签名或门禁记录。

旧版本文包含的直接合并、整树覆盖、全量暂存和推送命令已经撤销。若需复现历史缺陷，
只能依据 [dev 分支历史审查报告](dev分支审查报告.md) 在一次性隔离克隆中进行，不能在真实仓库执行。

## 2. 发布真源与制品链（DRAFT）

```text
origin/dev@cutoff Src blobs
  + committed catvba_refactor sources/config/schema/generator
  + exact source bindings and resolver receipt
  -> frozen input receipt (G0)
  -> immutable candidate Build Kit (G1)
  -> clean CATIA R28/B28 build environment (G2)
  -> new CATVBA imported from blank project (G3)
  -> AB3-only / MD2-only / HD2-only Core matrix (G4)
  -> returned artifact audit + signature/ACL/package (G5)
  -> controlled pilot + rollback drill (G6)
  -> human release approval bound to exact hashes (G7)
  -> publisher releases the already-approved immutable asset
```

Build Kit 是目标机构建输入，不是可安装 CATVBA。G1 Kit 必须明确记录：

```yaml
catvba_artifacts: []
compile_status: not-run
release_eligible: false
```

发布器不得负责选择源码、构建 CATVBA、推断许可证、执行目标测试或授予批准；它只能验证并发布
一个已经由 G7 receipt 精确绑定的不可变资产。

## 3. 门禁状态（DRAFT）

| Gate | 名称 | 当前状态 | 通过时至少需要 |
|---|---|---|---|
| G0 | INPUT-FROZEN | `NOT_RUN` | clean tree、accepted sync-record path/blob/hash/evidence commit、upstream cutoff/tree、overlay tree/manifest SHA、source binding、resolver 清单和审批范围 |
| G1 | KIT-READY | `NOT_RUN` | 全部离线检查、kit manifest、kit/ZIP SHA、确定性重建、`KIT_COMPLETE` |
| G2 | B28-ENV-ATTESTED | `BLOCKED` | R28/B28、SP/HF、VBA7/64、References、DSLS/profile 环境证明 |
| G3 | BUILT-UNVERIFIED | `BLOCKED` | 空白工程导入、Compile、保存/关闭/重开、候选 CATVBA 与构建记录 |
| G4 | CORE-MATRIX-PASS | `BLOCKED` | 三个隔离 profile 逐工具、逐文档类型、异常/取消/重启矩阵 |
| G5 | SECURITY-PACKAGE-PASS | `BLOCKED` | 返回制品源码/FRX/引用/p-code 审计、签名或 ACL、哈希和安装包 |
| G6 | PILOT-READY | `BLOCKED` | 受控试点、现场调试、监测、安装与回滚演练通过 |
| G7 | RELEASE-APPROVED | `BLOCKED` | 未过期的 G0-G6、风险接受、双人/企业审批、精确发布资产映射 |

草案中门禁状态只能是 `NOT_RUN`、`PASS`、`FAIL`、`BLOCKED` 或 `EXPIRED`。upstream cutoff/tree、
overlay identity、override binding、manifest、schema、generator 或冻结策略变化时，原 PASS 不得复用于
新 candidate，必须从 G0 建立新门链；SP/HF、引用或构建环境变化从 G2 重跑，候选二进制变化从 G3
重跑，DSLS/profile 变化从 G4 重跑。旧 Kit/receipt 对其原输入元组仍是不可变历史证据；只有明确的
安全撤回或有效期决定才标 `withdrawn`/`EXPIRED`，被新版本取代只标 `superseded`。当前 lineage 的
任何上游门不是有效 `PASS` 时，下游不得继续显示有效 `PASS`。

有效的 G0-G6 全部通过后才能称为 `pilot-ready`；G7 通过后才能称为
`release-approved` 或 Production 制品。

## 4. 上游吸收与发布分支（DRAFT）

- `origin/dev` 是 `Src/`、`resources/` 的唯一分支级上游；每次 fetch 固定旧 cutoff B、新 upstream U 和本地 pre-intake O。
- O 必须是 clean committed pre-intake HEAD；B 必须等于 O 最新 accepted sync record（首次为 initial
  baseline receipt）引用的 cutoff，并同时是 O 与 U 的祖先；最终 merge 第一父提交为 O、第二父提交为 U。
- upstream 若占用 `catvba_refactor/**`、改变 override base、产生 portable path/VB_Name/FRM-FRX 冲突，intake fail-closed。
- 通过显式 merge commit 吸收已审查的 dev 变化；intake 不混入新业务功能，已生成 Kit/证据的提交不 rebase。
- `origin/main` 只作旧发布和 workflow 观察源，不合入重构分支；main-only 修复只能重新形成有来源记录的 namespaced override 或治理 patch，不直接写 `Src/`。
- 每个 Kit 记录 `upstream-dev-cutoff`、upstream tree、overlay tree、manifest SHA 和 resolver 最终清单；远端后续更新不会静默改变已冻结输入。
- upstream 或 overlay 前移时，旧 Kit 标为 `superseded` 且不得用于新 candidate；只有安全判定明确撤回
  时另标 `withdrawn`。两种情况都为新 snapshot 重新冻结和构建，不改写旧 receipt。
- merge M 完成后，必须由单父 evidence commit E 写 post-merge sync record R；R 绑定 M/双亲/tree
  但不自报自身 hash，E 不改产品/overlay/manifest。发布只接受 E 祖先链中 schema/审批 accepted、
  且 path/blob OID/raw SHA-256 可复算的 R；禁止用可变 Git notes。
- 未来发布线应从共享 dev 历史建立受保护 `release/r28`，经 PR 和受保护环境审批；当前任务不修改远端。

详细本地结构和 intake 流程见 [PROJECT_STRUCTURE.md](PROJECT_STRUCTURE.md)。

## 5. Build Kit 与 B28 构建要求（DRAFT）

### 5.1 离线 Build Kit

至少包含：

- kit/snapshot ID、source commit、accepted sync-record path/blob OID/raw SHA-256/evidence commit、
  upstream cutoff/tree、overlay tree/manifest SHA、clean-tree 证明；
- 每个 resolved member 的 source ID/mode/role/选中侧/resolved path，以及适用的 upstream/local
  path/blob OID/SHA；
- 每个 Form 的原子 bundle ID、同侧整体选择、FRM/FRX 完整性和 `OleObjectBlob` 核对结果；
- resolver 最终组件清单及逐项来源（upstream/new/override/generated）；
- 输入文件逐项 portable path、原始字节 SHA、编码和分类；
- source/package/capability/tool/reference manifest 与 schema 版本；
- 分包源码、生成模块、确定性导入顺序、允许 References；
- 目标测试计划、证据模板、构建/安装/回滚手册；
- 整包和逐文件 `SHA256SUMS`、ZIP SHA、生成器版本；
- 明确的 `compile_status=not-run` 和 `release_eligible=false`。

### 5.2 B28 目标机构建

1. 证明机器、CATIA R28/B28、SP/HF、VBA7 64 位、DSLS 与 References 状态；
2. 从空白 CATVBA 工程导入，不使用旧二进制 `Save As`；
3. 只启用允许清单中的 B28 引用，确认无 MISSING、B30、x86、Temp 或用户目录污染；
4. 执行 Compile，保存、关闭 CATIA、重新打开、再次 Compile/HealthCheck；
5. 记录全部日志、截图/导出、操作者、时间、输入 Kit ID 和候选 SHA；
6. 将候选 CATVBA 返回离线审计，不在 Production 路径继续编辑。

### 5.3 Core 许可证矩阵

每个 Core 工具必须分别在 AB3-only、MD2-only、HD2-only profile 验证，不能使用三者同时存在的
组合会话代替。任一 profile 不可用的功能不得进入 Core：

- 仅部分基线 profile 可用：Baseline Extension；
- 需要 SPA、ST1、DL1、LO1、DMN、FTA、KWA、Excel 等：Licensed Optional；
- 每个非 Core 包都需独立库、引用、入口、安装、证据和失败隔离；
- 无额外许可证替代方案应优先采用 Core 可用的只读报告、人工步骤或禁用入口，不做隐式降级。

## 6. 当前 GitHub workflow 的定位与替代草案

`.github/workflows/auto-release.yml` 当前必须视为 **ineligible / disabled-by-policy**，即使文件仍存在。
已知问题包括：tag 归属判断不足、Linux runner 不能执行 B28 Compile、从仓库 glob 旧二进制、
缺少唯一资产与哈希校验、缺少 G7 receipt、没有受保护 Production 环境审批，且会直接创建正式 Release。

未来工作流建议拆成两阶段；该拆分仍待单独设计批准：

1. `release-validate` 只验证批准提交、kit ID、G7 receipt、资产白名单和全部哈希，产出不可变发布包；
2. `publisher` 经受保护 Production 环境人工批准后下载该包并发布，不重新 checkout 后选择文件。

在工作流完成单独设计、测试和审批前，不修改 tag 以“试运行”当前工作流。

## 7. G7 批准与发布记录（DRAFT）

G7 receipt 必须直接记录或通过不可变、逐哈希引用的 G0/Kit/sync receipt 绑定：

- 版本、批准 Git commit/tree、upstream cutoff/commit/tree；
- candidate overlay tree OID、manifest SHA；任何 dev synthetic digest、snapshot 或 plan 均不得进入 G7；
- resolver receipt ID/SHA、最终组件清单摘要、sync-record path/blob OID/raw SHA-256 及 evidence commit E；
- Kit ID、snapshot ID/mode、kit manifest SHA、Build Kit/ZIP SHA；
- B28 build ID、CATVBA SHA、References 与环境摘要；
- G0-G6 evidence URI、状态、时间、审批人和有效期；
- 许可证矩阵、已知风险、隔离包和无额外许可证替代方案；
- 签名证书摘要或 ACL/双人审批例外；
- 精确发布资产路径、大小、SHA 和允许的 publisher workflow 版本。

版本、tag、批准提交、upstream/overlay tree、manifest、resolver/sync/kit receipt、G7 receipt 和
CATVBA 哈希必须一一对应。发布完成后追加
tag object/commit、workflow run ID、Release ID、资产摘要和最终下载校验结果。

## 8. 安装与回滚（DRAFT）

- 版本并存安装到受管、普通用户只读目录，不覆盖旧目录；
- Production 与 Debug 物理分离，现场调试产物有 build ID、到期时间且不能提升为正式版本；
- 切换受管宏库注册/指针完成升级或回滚，不热改 CATVBA；
- 回滚只允许回到以前有完整 G7 发布记录、哈希仍匹配且未 withdrawn 的 R28 制品；
- 被新版本正常取代的制品标 `superseded`，仍保留原输入历史证据；存在安全/完整性问题的制品经明确
  决定标 `withdrawn`。两者都不删除或复用 tag，修复发布新补丁版本；
- CATVBA 回滚不等于模型数据回滚，CATPart/CATProduct/CATDrawing 数据恢复使用独立备份方案；
- 演练必须验证安装前状态、切换、恢复时间、用户配置、日志和失败后的人工接管。

## 9. 每次发布审查清单（DRAFT）

- [ ] [STATUS.md](STATUS.md) 显示 `release_eligible=true` 且 G7 为未过期 `PASS`
- [ ] source commit/tree、upstream cutoff/commit/tree、overlay tree OID 和 clean-tree 记录一致
- [ ] manifest SHA、resolver receipt、sync-record path/blob/hash/evidence commit 与最终组件清单可端到端复算
- [ ] snapshot ID/mode、Kit manifest、schema/generator、kit/ZIP/逐文件 SHA 一致且均为 candidate
- [ ] 正式 B28 SP/HF、VBA7/64、References 和三隔离 profile 有原始证据
- [ ] Compile、关闭/重开、再次 Compile、HealthCheck 和 Core 矩阵通过
- [ ] 返回 CATVBA 的模块、FRX、References、p-code、签名/ACL 和 SHA 审计通过
- [ ] Baseline Extension / Licensed Optional 未污染 Core，替代实现已记录
- [ ] 试点、现场调试边界、安装和回滚演练通过
- [ ] G7 receipt、审批人、有效期和精确资产映射完整
- [ ] publisher 只读取获批不可变包，不从仓库猜测资产
- [ ] 发布后 Release/资产摘要和最终下载哈希已回填

任一项缺失、过期或哈希不匹配，结论都是 **NO-GO**。
